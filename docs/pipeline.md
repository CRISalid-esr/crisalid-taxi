# 🔄 Data Pipeline & State Management

At FastAPI server startup (except in the test environment), an initialization pipeline (`StartupPipeline`) runs automatically to read, structure, vectorize, and index the OpenAlex taxonomy inside OpenSearch.

---

## 📂 Expected OpenAlex Data Structure

The data loader (`OpenAlexLoader`) looks for NDJSON snapshot files in the directory pointed to by `OPENALEX_DATA_PATH`. This directory must follow the structure below (generated by the OpenAlex snapshot downloader):

```
/data/openalex/
├── domains/
│   └── YYYYMMDD/
│       └── part_X.ndjson
├── fields/
│   └── YYYYMMDD/
│       └── part_X.ndjson
├── subfields/
│   └── YYYYMMDD/
│       └── part_X.ndjson
└── topics/
    └── YYYYMMDD/
        └── part_X.ndjson
```

---

## ⚡ Incremental Indexing & State Tracking

To avoid generating vector embeddings redundantly (which is a costly operation both in time and AI API requests) at each server startup, a state manager (`StateTracker`) is implemented:

1.  **Collect modification times**: At startup, the pipeline recursively scans each data subfolder (`domains`, `fields`, `subfields`, `topics`) and retrieves the maximum last modification time (`max_mtime`) of all files inside it.
2.  **State File**: These timestamps are compared against values previously recorded in the local state file: `/tmp/.taxi_state.json`.
3.  **Execution logic**:
    *   **No changes detected**: If no directory level has a modification time greater than the recorded one, the pipeline logs a success message and **skips** the AI embedding generation and OpenSearch indexing phases entirely.
    *   **Changes detected**: If one or more levels of the hierarchy have been modified (or if the state file does not exist), only the modified levels are processed. Their formatted text payloads are generated and sent to the embedding API.
4.  **Save state**: Once OpenSearch indexing is complete, the `/tmp/.taxi_state.json` file is updated with the new `mtime` values.

---

## 🎨 Constructing Text for Embeddings

The raw text payload sent to the AI embedding model is generated by `build_embedding_text` through the ordered concatenation of textual values:
*   For a **Domain**: Its `display_name` and `description`.
*   For a **Field**: Its name, description, and the parent Domain's `display_name`.
*   For a **Subfield**: Its name, description, and parent Field and Domain names.
*   For a **Topic**: Its name, description, `keywords`, and the entire parent hierarchy.

---

## 🔍 Indexing into OpenSearch

The generated embeddings are L2-normalized (making the dot product equivalent to cosine similarity) and sent in bulk requests to OpenSearch.

If the `openalex_embeddings` index does not exist, the pipeline creates it on the fly with the following KNN mapping configuration:
*   **Engine**: `nmslib`
*   **Algorithm**: `hnsw` (Hierarchical Navigable Small World)
*   **Metric**: `cosinesimil` (cosine similarity)
*   **Additional fields**: `type` (taxonomy hierarchy level) and `display_name` (original display name).
